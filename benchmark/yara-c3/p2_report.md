## target: yr_rules_scan_mem

### P2.1 Init Sequence
**Claim:** Before calling `yr_rules_scan_mem`, the caller must (1) call `yr_initialize()` once (global library init), (2) build a `YR_RULES*` object via the compiler pipeline: `yr_compiler_create(&compiler)` → `yr_compiler_add_string`/`yr_compiler_add_file`/`yr_compiler_add_fd`/`yr_compiler_add_bytes` to parse rule source → `yr_compiler_get_rules(compiler, &rules)` to obtain the compiled `YR_RULES*`, then `yr_compiler_destroy(compiler)` (compiler not needed after rules are extracted). Alternatively `rules` can come from `yr_rules_load()`/`yr_rules_load_stream()` (precompiled rules), which also populates `ext_vars_table`. No ordering is required between `yr_initialize()` and `yr_compiler_create()` other than init-before-use.
**Evidence:**

### P2.3 Object Lifecycle
**Claim:** `yr_rules_scan_mem` itself creates and destroys a short-lived `YR_SCANNER` internally for each call: create → set_callback/set_timeout/set_flags → scan → destroy. The `YR_RULES*` is *not* owned by the scan call: it must be created before and destroyed by the caller after all scans are done, via `yr_rules_destroy(rules)`. The caller may call `yr_rules_scan_mem` (or `_scan_file`/`_scan_fd`) multiple times against the same `rules` object; each call is independent (fresh scanner each time).
**Evidence:**
> libyara/rules.c:214-225: `GOTO_EXIT_ON_ERROR(yr_scanner_create(rules, &scanner)); yr_scanner_set_callback(...); yr_scanner_set_timeout(...); yr_scanner_set_flags(...); result = yr_scanner_scan_mem(scanner, buffer, buffer_size); yr_scanner_destroy(scanner);` — full create/configure/use/destroy sequence inside the target itself.
> libyara/include/yara/rules.h:125: `YR_API int yr_rules_destroy(YR_RULES* rules);` — the rules object lifetime is caller-managed, separate from the scanner.
> tests/oss-fuzz/dex_fuzzer.cc:6,40-46: a single global `rules` created once in `LLVMFuzzerInitialize`, then `yr_rules_scan_mem` called repeatedly (once per fuzz iteration) without recreating `rules`.

### P2.4 Return Value Handling
**Claim:** Return value is an `int` error code; `ERROR_SUCCESS` (0) means scan completed without a fatal scan error — it does NOT by itself indicate whether any rule matched (matches are reported via callback messages, not the return value). Non-zero values are error codes such as `ERROR_INSUFFICIENT_MEMORY`, `ERROR_CALLBACK_REQUIRED`, `ERROR_TOO_MANY_MATCHES`, `ERROR_SCAN_TIMEOUT`, `ERROR_EXEC_STACK_OVERFLOW`, etc. Harnesses typically ignore the return value's exact code but should not treat a non-zero code as a crash signal (it is expected on timeouts, too-many-matches, bad callback, etc.).
**Evidence:**
> libyara/rules.c:215: `int result = ERROR_INTERNAL_FATAL_ERROR;` initial pessimistic value, overwritten on success/paths.
> libyara/scanner.c:477-481: returns `ERROR_CALLBACK_REQUIRED` when callback is NULL.
> tests/test-exception.c:152-158: caller checks both `rc` and a match counter: `if (rc == ERROR_SUCCESS || counters.rules_matching != 0) return 1;` — shows return code alone is not match indication.
> libyara/include/yara/error.h:100: `#define ERROR_CALLBACK_REQUIRED 53` (one of many error codes returned).

### P2.5 Cleanup Sequence
**Claim:** On both success and error return from `yr_rules_scan_mem`, the internal `YR_SCANNER` is already destroyed by the function itself (`yr_scanner_destroy(scanner)` on the success path, line 225; on early failure via `GOTO_EXIT_ON_ERROR` it jumps to `_exit` before scanner creation succeeded, so nothing to free). The caller's responsibility is only the `YR_RULES*` (`yr_rules_destroy`) and, if a compiler was used, `yr_compiler_destroy` (already done before scanning) — plus any buffer/file mapping used to build `buffer`. If `yr_rules_scan_file`/`yr_rules_scan_fd` was used instead, `yr_filemap_unmap(&mfile)` is called automatically inside those wrappers.
**Evidence:**
> libyara/rules.c:217-225: scanner destroy happens inside the function right after the scan, regardless of `result`.
> libyara/rules.c:251-261: `yr_rules_scan_file` calls `yr_filemap_map`, then `yr_rules_scan_mem`, then `yr_filemap_unmap(&mfile)` — self-contained cleanup of the file mapping.
> libyara/include/yara/rules.h:125: `yr_rules_destroy(YR_RULES* rules)` — caller-level cleanup for the rules object, to be called once scanning is fully done (e.g. after fuzzing loop, not per-iteration).

### P2.10 Behaviour Controls
**Claim:** Behaviour-selecting parameters/flags around the target: `flags` bitmask passed to `yr_rules_scan_mem`/`yr_scanner_set_flags` — `SCAN_FLAGS_FAST_MODE` stops matching after the first hit per rule-relevant path; `SCAN_FLAGS_PROCESS_MEMORY` changes entry-point detection (`yr_get_entry_point_address` vs `yr_get_entry_point_offset`) and governs whether the buffer is treated as a mapped process image vs. a file; `SCAN_FLAGS_NO_TRYCATCH` disables the `YR_TRYCATCH` fault-handling wrapper around block fetch/scan (oss-fuzz fuzzers always pass this to avoid false "crash" reports from fault injection testing, see dex_fuzzer.cc:44); `SCAN_FLAGS_REPORT_RULES_MATCHING`/`SCAN_FLAGS_REPORT_RULES_NOT_MATCHING` select which callback messages get emitted (default both, set in `yr_scanner_create`). `timeout` (seconds, converted to ns) gates a stopwatch check during the scan loop causing `ERROR_SCAN_TIMEOUT`. `callback`'s return value (`CALLBACK_CONTINUE`/`ABORT`/`ERROR`) changes whether `yr_scanner_scan_mem_blocks`/`yr_execute_code` keep iterating. External variables set via `yr_rules_define_integer/boolean/float/string_variable` select different branches of compiled rule conditions evaluated by `yr_execute_code` (OP_PUSH_EXTERNAL* opcodes), without altering the call graph.
**Evidence:**
> libyara/include/yara/scan.h:38-42: flag bit values.
> libyara/scanner.c:259-261: default flags set in `yr_scanner_create`: `SCAN_FLAGS_REPORT_RULES_MATCHING | SCAN_FLAGS_REPORT_RULES_NOT_MATCHING`.
> libyara/scanner.c:522-544: `YR_TRYCATCH(!(scanner->flags & SCAN_FLAGS_NO_TRYCATCH), {...})` and `if (scanner->flags & SCAN_FLAGS_PROCESS_MEMORY) scanner->entry_point = yr_get_entry_point_address(...) else ... yr_get_entry_point_offset(...)`.

### P2.11 Input Expectations
**Claim:** `buffer`/`buffer_size` have no required header or terminator — `yr_rules_scan_mem` treats the buffer as an opaque byte array of exactly `buffer_size` bytes (can be 0). Internally it wraps it as a single `YR_MEMORY_BLOCK` (`block.size = buffer_size; block.base = 0; block.context = (void*) buffer;`) with a static one-shot iterator (`_yr_get_first_block`/`_yr_get_next_block` returning NULL after the first call), so the whole buffer is presented to the Aho-Corasick scanner as one contiguous block. There's a size-based fast-path check: if `buffer_size > YR_FILE_SIZE_THRESHOLD` and the AC root state has any transition, it logs/handles the "slow scanning of large files" case specially. No format assumptions (PE/ELF/etc.) are made by `yr_rules_scan_mem` itself — format-specific parsing only happens inside optional YARA modules (pe/elf/dex/macho/dotnet) that the compiled rules may `import`, and even then module parsers are expected to handle malformed/truncated data gracefully (that's what the pe/elf/macho/dotnet oss-fuzz fuzzers specifically target, by importing those modules and letting the condition VM invoke the module's own parser on `buffer`).
**Evidence:**
> libyara/scanner.c:718-731 (`yr_scanner_scan_mem`): construction of a single in-memory `YR_MEMORY_BLOCK`/iterator from `buffer`/`buffer_size`.
> libyara/scanner.c:653-665 (`_yr_get_next_block`): "default iterator; single memory block, blocking" — always returns NULL, i.e. exactly one block is scanned.
> libyara/scanner.c:733-739: `if (scanner->rules->ac_match_table[YR_AC_ROOT_STATE] != 0 && buffer_size > YR_FILE_SIZE_THRESHOLD) { ... }` — size-dependent behaviour but not a hard limit/rejection.
> tests/test-api.c:627: scanning a 0-byte buffer (`""`, size 0) is valid and used in the test suite.
> tests/oss-fuzz/pe_fuzzer.cc / macho_fuzzer.cc / dotnet_fuzzer.cc / dex_fuzzer.cc: each imports a format module and feeds raw fuzz bytes directly as `buffer`, confirming no pre-validation/header is required by `yr_rules_scan_mem` before invoking module parsers through the condition VM.

### Other entries — call protocol and combination with the target

**yr_rules_scan_mem_blocks** — entry allowing a custom `YR_MEMORY_BLOCK_ITERATOR` (multi-block / non-contiguous scanning). Needs: same prerequisite `YR_RULES*` as the target, plus caller-built `YR_MEMORY_BLOCK_ITERATOR` with `first`/`next`/`file_size` callbacks and `last_error` initialized (see libyara/include/yara/types.h iterator struct, and libyara/scanner.c:486-520 handling `ERROR_BLOCK_NOT_READY` re-entry). Internally calls `yr_scanner_create`→set_callback/timeout/flags→`yr_scanner_scan_mem_blocks`→`yr_scanner_destroy` (libyara/rules.c:183-193), mirroring the target's lifecycle exactly but swapping the mem-block construction step. Returns same int error codes. In a harness this would be used instead of `yr_rules_scan_mem` when exercising the multi-block / `ERROR_BLOCK_NOT_READY` code paths; it is not required alongside the target, it is an alternative entry into the same core.
Evidence: libyara/rules.c:172-194.

**yr_rules_scan_file** — needs a real filename (`yr_filemap_map` memory-maps it); internally delegates straight into the target (`yr_rules_scan_mem`) with the mapped data/size (libyara/rules.c:241-262), then calls `yr_filemap_unmap(&mfile)`. For a fuzz harness operating on in-memory buffers, this is typically not used directly (it requires writing fuzz data to a temp file first); it exists as a convenience wrapper around the target for file-based callers.

**yr_rules_scan_fd** — same as scan_file but via `YR_FILE_DESCRIPTOR` (`yr_filemap_map_fd`), also delegates into `yr_rules_scan_mem` (libyara/rules.c:264-281) and unmaps on completion. Same caveat as scan_file re: fd must be a valid open/mappable file.

**yr_rules_define_integer_variable / yr_rules_define_boolean_variable / yr_rules_define_string_variable / yr_rules_define_float_variable** — must be called on an already-compiled `rules` (after `yr_compiler_get_rules`/`yr_rules_load`) and BEFORE `yr_rules_scan_mem`, since the scanner copies/reads `rules->ext_vars_table` values into its `objects_table` at `yr_scanner_create` time (libyara/scanner.c:305-327: `external = rules->ext_vars_table; while (!EXTERNAL_VARIABLE_IS_NULL(external)) { yr_object_from_external_variable(external, &object); ... }`). Changing an external variable's value after a scanner has already been created for that scan has no effect on that particular call (a new scanner is created fresh on each `yr_rules_scan_mem` call, so a `define_*` call made between two `scan_mem` calls does take effect for the next call). Each returns `ERROR_SUCCESS`, `ERROR_INVALID_ARGUMENT` (identifier NULL or not found), or `ERROR_INVALID_EXTERNAL_VARIABLE_TYPE` (type mismatch with how the variable was declared at compile time via `yr_compiler_define_*_variable`). For `yr_rules_define_string_variable` specifically, an existing `EXTERNAL_VARIABLE_TYPE_MALLOC_STRING` value is freed via `yr_free` before `yr_strdup(value)` replaces it (libyara/rules.c:151-163) — no caller-side cleanup needed for this value; it is owned/freed by the rules object's lifecycle (`yr_rules_destroy`) or replaced by subsequent `define_string_variable` calls. These functions require the identifier to have been pre-declared (at compile time with `yr_compiler_define_*_variable`, or already present if `rules` loaded from a `.yarc` file produced from rules compiled with external vars) — calling them with an unknown identifier returns `ERROR_INVALID_ARGUMENT` and has no effect; they do not create a scan-time side effect by themselves until the next `yr_rules_scan_mem`/`yr_rules_scan_mem_blocks`/`yr_rules_scan_file`/`yr_rules_scan_fd` call creates a new scanner and re-reads `ext_vars_table`.
Evidence: libyara/rules.c:44-169 (all four functions); libyara/scanner.c:305-327 (ext var consumption at scanner creation); cli/common.c:139-206 (`define_external_variables` real usage pattern distinguishing compiler-time vs rules-time definition).
